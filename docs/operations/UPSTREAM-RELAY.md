# The upstream relay - a logged, scoped, cost-capped line to upstream

Built under ACT-69 (2026-10-13). Code: `scripts/upstream_relay.py`. Settings: `docs/operations/relay_config.json`. Tests: `tests/test_upstream_relay.py`.
QA-REGISTER A64, TOOLING row `scripts/upstream_relay.py`. This document contains no secrets and is safe in the public repo.

## What it is

Until now the operator copied our notes into a Gemini chat (upstream, the research partner) and pasted the replies back. The relay lets Claude do that exchange directly,
through the Gemini REST API, with a record of every message and a hard limit on cost. It is text only: there is no Google Search, no grounding, no code execution and no
tools of any kind in the request. It is NOT wired to any scheduled task; it is run by hand.

The stateless API is given a briefing pack as its system prompt, built fresh from repo files each time: the contract (`pipeline-contract.md`), upstream's promises
(`upstream_commitments.csv`), the ids they gave us (`given_ids.csv`) and the last three notes to upstream. It is capped (`briefing_max_chars`) and its hash is printed on every send.

## Scope (agreed with the operator, 2026-10-13)

Start with routine id requests and fact confirmations. Anything about rulings, the contract or money goes to the operator first. The relay cannot tell the difference by itself,
so the rule is in the policy below: only notes generated by our own code from verified data go without approval.

## Policy classes (what `send` allows)

| kind | without approval | with `--operator-approved` |
|---|---|---|
| `id_request`, `fact_confirmation` | only when `--provenance` names a generator in the allowlist (`customer_awards-request`, `release-gate`) | yes |
| any of those two with free text (no or unknown provenance) | refused | yes |
| `question`, `troubleshoot` | always refused | yes |

`--operator-approved` means the operator has read that exact note. Provenance is a tag the calling code asserts; the allowlist lives in `relay_config.json`. The content guard
applies to every send, approved or not.

## The content guard

A send is BLOCKED (nothing stored, nothing sent) when the note contains: a key-like token (`AIza...`, `AQ....`, `sk-...`, a long base64-like string), the word password,
passwd, secret or private_key followed by a value, any e-mail address, a service-account JSON marker, an SMTP setting name, or raw customer-sheet rows (a row with more than
five columns that carries the customer's PRIORITY and STATUS style fields). Names and URLs of awards and conferences are allowed: upstream already has them. The journal
records the labels of what tripped the guard, never the matched text. The briefing pack is also checked for secrets.

## Cost caps

Before every call the relay estimates tokens (3 characters per token, deliberately high) and assumes the full `max_output_tokens` is used, then prices that from
`relay_config.json`. It refuses and says "stop and ask" when the estimate is over `per_call_cap_usd` (default 0.10) or when this ISO week's spend plus the estimate is over
`weekly_cap_usd` (default 2.00). After a call it prices the real token counts the API reports. The journal is the usage ledger. A model with no price in the config is refused.

**Prices are estimates written by the builder from memory. The operator verifies them** at https://ai.google.dev/gemini-api/docs/pricing (paid tier, text input and output, for
the exact model id in the config) and corrects `prices_usd_per_1m_tokens`. A typical id request costs well under one cent; a ping costs a fraction of a cent. The operator's own
spend cap on the separate AI Studio project is the real backstop; the relay caps are the first line.

## The journal

Outside the repo, in `C:\Users\matts\AppData\Local\CFP-Monitor\runs_out\relay\`:

- `journal.jsonl` - append-only, one JSON line per message: id, UTC time, kind, provenance, model, direction (`out` = sent by us, `in` = reply), sha256 of the full text, character
  and token counts, estimated and actual cost, decision (`sent`, `received`, `blocked`, `dry-run`, `error`) and the reason. Each line carries the hash of the previous line, so an
  edited or removed line is detectable.
- `messages/<id>_out.txt`, `<id>_in.txt`, `<id>_dryrun.txt` - the full texts (they may name customer awards). Written once, never overwritten, never deleted by the tool.
- `replies/<id>/ids_reply.csv` - written only when a reply contains a recognised ids table.

Read it: `python scripts/upstream_relay.py journal verify` re-hashes the chain and every stored text and exits 1 on any edit, missing file or unreferenced file. To read the
history, open `journal.jsonl` (one line per message) and the matching file in `messages\`.

## How a reply is handled

A reply is DATA. It is saved, hashed, redacted of anything key-shaped and shown to the operator as untrusted text. Nothing in it is ever executed or applied, and if it contains
instruction-like text ("run the following", a shell code block) the tool says so. For an ids table with exactly the columns of `docs/operations/award_ids_reply_*.csv`
(`market,award_name,action,event_id,survivor,note`; actions NEW, RELABEL, STAMP_EXISTING, STAMP_NONAWARD) it writes `ids_reply.csv` and prints the next, manual, step:

    python scripts/customer_awards.py --reply <that ids_reply.csv> --reply-plan

which only checks the reply against the awards list (see `customer_awards.py`). Stamping (`stamp_given_ids.py`) and `check_delivery_ids.py` stay separate, deliberate steps.

## How to run it

    python scripts/upstream_relay.py ping                      # proves the line: model, tokens, estimated cost
    python scripts/upstream_relay.py models                    # lists usable models, writes the newest cheapest flash text model to the config
    python scripts/upstream_relay.py send --note FILE --kind id_request --provenance customer_awards-request --dry-run
    python scripts/upstream_relay.py send --note FILE --kind question --operator-approved
    python scripts/upstream_relay.py journal verify

`--dry-run` does everything except the network call: it checks policy, guard and cost, and writes the would-be message and the estimate. A draft such as
`runs_out\qa\<date>\request_to_upstream_awards_<date>.md` (made by `customer_awards.py`) is the usual note for `--kind id_request --provenance customer_awards-request`.
Failures are printed with the exact HTTP status and error text (the key is never in it); 429, 5xx and network errors are retried at most twice, each retry announced.

## The key and how to rotate it

The key is the user-level environment variable `CFP_RELAY_GEMINI_KEY`, from a separate AI Studio project with a spend cap set by the operator. The relay reads the process
environment first and then the Windows user environment (a terminal opened before the variable was set does not see it). The key is sent only in the `x-goog-api-key` header,
never in a URL, and every printed line, file, journal entry and error message is redacted. It is not checked by prefix (newer keys start `AQ.`). The relay may report its length.

To rotate: create a new key in the AI Studio project, set the user environment variable to the new value (Windows: Settings > System > About > Advanced system settings >
Environment Variables), delete the old key in AI Studio, open a new terminal and run `ping`. Never paste the key into a chat, a note, a file in this repo or a commit.
If a key is ever suspected to have leaked (for example it appears in a log), delete it in AI Studio at once and rotate.

## Limits worth knowing

- A reply from a language model without tools is not research: it cannot see a page. Treat a reply as the partner's claim, and check ids and dates with the existing validators.
- The briefing pack is a summary of the contract, not a memory: each call is independent. Put what the answer depends on in the note itself.
- The guard is pattern based. It cannot know that a sentence is confidential; the operator approves every free-text note for that reason.
